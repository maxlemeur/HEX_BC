# Remaining affaire performance failures, defined before implementation

The `remaining affaire performance` TesterArmy journey owns a new local ARMY project, a historical engine-2 draft with one section and 1,000 priced lines, and two register entries. It refuses a hosted backend or a missing owned-stack marker. Seeding uses the existing native SQL transport only after application creation, tenant/owner checks and an authenticated API read. The same retained receipt is reused for baseline and candidate within that stack. No existing customer affaire is visited.

| Failure | Observable check |
| --- | --- |
| Repeated register reads delay a fiche | Five real list-card transitions, click-to-heading timing, completed server-fetch counts and durations correlated by wall-clock intervals. Duplicate register gate/project reads are recorded before a reduction is asserted. |
| Margin analysis unnecessarily blocks approval and output checks | Trace the independent margin and approval/finish-line requests on the same 1,000-line draft; compare identical baseline/candidate navigation, without attributing every timing difference to code. |
| Deduplication escapes a request or retains stale register data | Change only this owned fixture's register text/status in SQL after the visits, reload, assert the new text and count, restore it and reload again; a fresh anonymous browser must still receive API 401 and a login redirect. |
| Authorization or financial values change | Same tenant/owner fixture, exact 1,000 lines and stored HT/TVA/TTC of 2,502,500 / 500,500 / 3,003,000 cents; same version edit link, financial summary, Versions and register sections. |
| Reordering reads starts approval writes without a successful initial load | Approval projection/audit reads remain dependent on the authorized successful core load. Review their write behavior explicitly; preserve their fresh uncached version reread and version-conflict check. |

`getEstimateApprovalSummary` calls `syncEstimateApprovalSummary(trigger: "read")`, which can persist the version approval projection and audit events. It must not be memoized or started before the required successful load. Intake workspace, register gate/page/timeline, direction signals and margin analysis are read-only on these paths. Finish-line checks still follow approval and its fresh version reread because their gating consumes the approval projection. Financial snapshots therefore establish financial stability, not total database immutability.

Only request-local reuse is allowed. No persistent cache, TTL, global authenticated context, permission/schema change or blanket cache of mutable workflow results is allowed. Next's installed guide is `node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`, section “Deduplicating requests”. Outside an RSC render, React cache does not create a cross-action cache.

Run under the production performance wrapper on the owned stack, with `E2E_DOGFOOD_OWNED_STACK=1`, existing SQL transport variables and `E2E_DOGFOOD_FETCH_LOG` pointing to sanitized server JSONL instrumentation. Baseline/candidate must use identical probe instrumentation and fixture. Server-fetch records contain paths, selected nonsecret query fields and timings, never headers, cookies, bodies or credentials. These local samples do not establish field percentiles or physical-phone performance.

## Decision after the measured baseline

The five complete baseline transitions each made one exact register gate read and one exact register project-access read. Next already deduplicates these identical network requests, so this lot adds no cache and claims no reduction of those network counts. The candidate explicitly reuses the register page's authorized context/project for its summary and timeline, overlaps their independent reads with the page query, and releases the approval dependency once the core summary/timeline/DPGF group succeeds. Margin analysis continues concurrently. Its dedicated full-card reader preserves a standalone v3 evolution notice even when no numeric analysis is calculable; the narrower existing analysis API keeps its previous contract.

The first baseline attempt failed in the test harness because this installed SDK does not support chaining `.locator()` from a locator. The correction uses a scoped semantic `getByText("2", { exact: true })` and `toHaveText("2")` (or `1` during freshness), preserving the exact open-point count. That attempt is not a performance pass. A later counter-label correction distinguishes the full gate projection by `source_file_name`, since another register projection also selects `scope_type`; retained raw server entries allow comparison without rewriting the original run.
