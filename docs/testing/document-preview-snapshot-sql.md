# Préparation du snapshot v2 pour l’aperçu PDF

Les modes de défaillance ont été définis avant toute nouvelle migration dans `.e2e/offer-emission/document-preview-precode-20261013-01/plan.md`. Le vrai scénario UI OF04 du 13 octobre 2026 échoue avant génération avec `OFFER_CLIENT_CONTRACT_ANCHOR_MISMATCH` : brouillon moteur 2, révision 9, contexte et révision figés NULL, cinq snapshots de ligne NULL, malgré un footer 2000/400/2400 centimes. Le diagnostic privé ne doit pas être exporté. Ce RED expose la préparation manquante ; il ne justifie pas de relâcher les contrôles de publication Client1/seal5.

La solution décidée est un RPC `freeze_estimate_v2_document_snapshot(uuid,uuid,timestamptz,bigint,uuid,uuid,jsonb,jsonb,jsonb)` sous rôle `service_role`, invoker, chemin vide, sans arguments par défaut. Le sixième argument est la session du bail, obligatoire. Il verrouille version → autorisation tenant actif/membership/projet owner ou admin → bail exact tenant/version/user/session non expiré, puis délègue au wrapper commercial existant avec son mode interne `send`. Ce mode financier ne crée aucun envoi ni approbation. Les deux fonctions financières existantes, leurs corps/OID/ACL et les gardes d’offre restent intacts. Le tenant fourni vient du contexte serveur authentifié : SQL contrôle son activité et les droits, sans prétendre vérifier `is_default`.

Avant le claim PDF, le serveur doit préparer le brouillon v2 sous son propre bail, puis relire version/items et leur CAS frais. La copie client et le PDF partagent cette image. Les tests SQL ne prouvent pas cet ordre UI : root le qualifie dans TesterArmy, depuis l’ouverture de la modal jusqu’au PDF réel.

## Défaillances et oracles définis avant code

| Admin calcule avec ses propres tarifs | `admin-project-owner-rate` : propriétaire engineer distinct de l’acteur admin ; rôle du propriétaire0ct/h, rôle de l’admin9999ct/h. Image attendue propriétaire. |
| Arrondi explicite perdu | `commercial-rounding` : FO2001×1, TVA calculée400, brut2401, nearest100→2400 ; ajustement−1, taxe ajustée399, image et footer réconciliés. |
| Gel rejoué inutilement ou non invalidé après édition | `exact-replay` compare tout l’état/audit après replay CAS frais ; `edit-refreeze` édite le titre, vérifie l’invalidation puis le nouveau gel sous bail. |
| Un autre onglet utilise le bail du même utilisateur | `same-user-other-session`, puis session NULL, absente, expirée ou possédée par un autre utilisateur. Aucun refus ne modifie l’état complet. |
| CAS périmé ou article changé durant le calcul | `stale-updated-at`, `stale-revision`, `edited-during-calculation`, contrôles exacts40001. Une course réelle reste non exécutée. |
| Acteur/rôle/tenant/projet interdit | viewer, director, autre engineer owner, autre tenant/actor/version, tenant inactif, membership supprimée, projet archivé. Rôles PG réels, claims précis et données synthétiques. |
| Mauvaise version ou contexte financier périmé | engine1, sending, tarif/flag/marge changés, rôle absent avec heures positives, contexte étranger ou clé inconnue. Les refus financiers existants restent autoritaires. |
| Projection non sûre | ligne absente/dupliquée/étrangère, snapshot NULL, centimes fractionnaires, footer non réconcilié, ajustement donnant une taxe calculée négative. |
| Client direct ou surcharge sans session | `catalog-all-overloads` inspecte toutes les surcharges ; une seule9args sans défaut, invoker, chemin vide, PUBLIC/anon/auth sans EXECUTE ; appels effectifs anon/auth refus42501. |
| Mutation partielle après écriture des lignes | `late-fault-after-lines` : trigger transactionnel vérifie les cinq snapshots réels avant fauteP9001 au contexte/version ; séquence temporaire nontransactionnelle prouve le hit, état complet identique. |
| Aperçu entraînant envoi, approbation, seal ou capacités | Chaque réussite garde draft, seal/markerNULL et compare toutes les lignes liées hors seuls dérivés financiers/audit technique. Refus/rollback incluent aussi tous les audits. |

Les contrôles de bail précis, rôles PG, late rollback et métadonnées de fonctions constituent une exception SQL justifiée : un navigateur ne peut pas directement exercer tous les grants/session UUID concurrents ni injecter une panne après la première écriture. Le scénario UI OF04 reste la preuve principale du résultat utilisateur. Le terme « concurrent » dans un cas désigne un état devenu périmé préparé séquentiellement ; aucune vraie course deux connexions n’est revendiquée.

## Fixture et runner

La fixture `src/test/fixtures/estimate-v2-document-snapshot-regression.sql` contient **40 cas**, tous écrits avant le nouveau wrapper. Préfixe dédié `dfca0700`, utilisateurs Auth/bootstrap réels insérés uniquement dans BEGIN, tenants/projets/sections/versions/baux synthétiques. Aucun compte persistant, Auth API ou donnée privée OF04 réutilisée. Rôle MO0 et section parent réelle évitent les raccourcis de setup. Chaque cas utilise un sous-rollback P9002 et le terminal P9001 obligatoire annule toute la fixture. Une signature absente est `missing-precondition`, une préparation échouée est une preuve manquante, jamais un faux RED des40cas.

Runner préparé dans `.e2e/offer-emission/document-preview-precode-20261013-01/run.py`, sans exécution DB par son auteur. Il accepte explicitement une nouvelle migration candidate, vérifie le SHA demandé, n’exécute son corps que dans la transaction de rollback et n’écrit jamais l’historique. Mode installé disponible sans `--migration` : aucune DDL n’est ajoutée à l’entrée psql. Les images avant/après inventorient **toutes** les tables r/p non partitions des schémas public/private/auth/storage, toutes leurs colonnes actuelles, l’historique applicatif complet, gardes catalogue/droits et toutes les fonctions/procédures. Corps SHA256 de `pg_get_functiondef`, OID, ACL, propriétaire, configuration et invoker sont comparés. Le candidat ne peut ajouter que le nouveau RPC, aucune ancienne fonction ne peut changer. P9001, exit3, liste exacte des40cas, compte des verdicts et source closure sont obligatoires.

Le packet conserve `before.json`, `after.json`, `cases.json`, `candidate-functions.json` (ou `installed-functions.json`), commande, SHA des sources et environnement exact. Entrée/stdout/stderr sont privés ; rapport public uniquement noms et SQLSTATE. Le runtime local admis reste celui fixé par root : localhost33485, API45585, identité PG vérifiée. Aucun reset, COMMIT, seed persistant, nettoyage ou arrêt du runtime partagé. La fenêtre DB reste exclusive à root.

Sans qualification root, ces fichiers constituent une préparation révisable, pas des tests passés. Même40GREEN ne prouvent ni PDF/HTML, transport, anciens PDF, contexte juridique, émission, seal cryptographique, recette utilisateur ou vraie concurrence. Les verrous suivent les garanties [PostgreSQL17](https://www.postgresql.org/docs/17/explicit-locking.html) ; les privilèges/invoker sont ceux de [CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html).

Première exécution locale candidate-20261013-01 : 39/40, terminalP9001 et conservation complète. Le cas not-draft a échoué pendant un UPDATE direct du statut sous postgres, refusé par la garde workflow existante; il n'a pas exercé le nouveau RPC. Correction de préparation uniquement : vraie réserve13arguments sous service_role, acteur/bail synthétiques dédiés, assertion sending avant l'appel puis préimage de refus complète. Oracle42501/REQUIRES_DRAFT, inventaire40 et DDL restent identiques. L'ancienne fixture est conservée dans le packet révision02. Aucun état sending n'est seedé dans une recette navigateur, aucune livraison ou donnée persistante créée par ce setup SQL.

Candidate02 puis diagnostic séparé : la réserve réelle refuse ESTIMATE_V2_SNAPSHOT_STALE tant que l'image financière v2 est absente. Le setup not-draft suit désormais l'ordre réel : gel par l'ancien freezer commercial installé (indépendant du wrapper testé), CAS frais, réserve13arguments, assertion sending, appel strict du nouveau wrapper. Les refus de production sont préservés;40cas/DDL/oracles demeurent inchangés.
