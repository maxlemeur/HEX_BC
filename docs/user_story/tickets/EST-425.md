## Best practices implementation
- Faire du classifieur une brique rapide et deterministe d'abord, avec heuristiques testables avant toute sophistication IA.
- S'appuyer sur MIME, extension, contenu minimal et signaux documentaires plutot que sur un seul critere fragile.
- Garder separe le resultat de classification, la recommandation de niveau et la decision finale pour conserver une trace claire du pourquoi.
- Rendre le warning comprehensible pour un chiffreur, pas seulement pour un developpeur.

## Notes execution
### Decisions techniques
- Le classifieur a ete implemente comme une brique pure partagee UI + serveur dans `src/lib/takeoff/document-classifier.ts`.
- Le serveur recalcule toujours la classification a la creation du job et ne fait pas confiance a un choix purement front.
- La trace d'override n'a pas necessite de migration DB: elle est persistee dans l'audit `takeoff.job.created` via `classification.*` et `selection.override_applied`.
- Le hub affaire consomme une recommandation serveur pour le `defaultPlanSetId`; le flow upload mono-fichier calcule la meme logique localement pour guider l'utilisateur avant submit.

### Risques residuels
- Les heuristiques restent basees sur `file_name`, `mime_type` et `page_count`; un document mal nomme ou pauvre en metadonnees peut etre mal recommande.
- Certains noms de fichiers contiennent des signaux contradictoires ou trompeurs. Exemple concret: `niveau-b.pdf` fait remonter un indice "plan" via `niveau`, ce qui peut pousser vers `C`.
- Les surfaces UI touchees (`TakeoffUploadForm`, `LaunchMetreDialog`, `AffaireHub`, `PlansStep`) sont partagees avec d'autres travaux en parallele; le risque principal est le conflit de merge, pas le contrat fonctionnel du ticket.
- La CI globale n'est pas entierement verte a cause d'erreurs TypeScript preexistantes hors scope sur l'async worker, le batch Gemini et certains tests `processor`.

### Comment les gerer
- Garder le classifieur deterministe et observable: toute evolution doit d'abord passer par des tests de fixtures realistes avant d'ajouter de nouveaux heuristiques.
- Ne pas utiliser le nom de niveau dans les fixtures de tests PDF quand on veut verifier une recommandation `B`; preferer des noms metier explicites comme `lot-cvc-dpgf.pdf`.
- En cas de doute produit sur une famille de documents ambigus, enrichir la table de signaux et la couverture de tests avant de modifier le wording UI.
- En integration multi-agents, isoler le commit `EST-425` sur les fichiers modifies par ce ticket et relire particulierement les conflits sur les composants d'entree takeoff.
- Pour la remise a plat CI, traiter dans un ticket dedie les erreurs `typecheck` hors scope avant d'utiliser la verteur globale comme critere de fermeture de `EST-425`.
