## Best practices implementation
- Concevoir une vraie state machine explicite plutot qu'une collection de `if`/`else` implicites sur les statuts.
- Garantir l'idempotence de la reconciliation via verrou logique, compare-and-swap ou cle de reprise stable.
- Isoler le mapping provider -> etat applicatif dans un module central testable.
- Documenter clairement retry, abandon et dead-letter pour eviter que les incidents batch finissent en bricolage manuel.

## Notes execution
- Decision technique:
  - Le worker existant `process_takeoff_job` est re-utilise pour la reconciliation durable. Aucun nouveau service n'a ete introduit.
  - Le processor Level A ne poll plus Gemini Batch jusqu'au terminal. Il soumet, persiste `provider_batch_*`, planifie `provider_reconcile_due_at`, puis rend la main.
  - La reconciliation s'appuie sur un lease logique atomique via `acquire_takeoff_batch_reconcile_lease(...)`, avec backoff dedie et dead-letter explicite `AI_TIMEOUT`.
  - `takeoff_jobs.status` reste `processing|completed|failed`; les etats provider restent portes par `provider_batch_state` et les outcomes worker `submitted_to_provider|awaiting_provider_result`.
  - Le batch durable est borne au niveau `A`. Les niveaux `B/C` restent executes en `sync` pour eviter un faux contrat.
- Risque residuel:
  - Le contrat actuel ne persiste qu'un seul `provider_batch_id` par job. Cela ne permet pas de representer proprement un niveau `B/C` batch avec plusieurs chunks ou reruns provider.
  - Correction proposee:
    - soit introduire une table enfant `takeoff_job_provider_runs` avec cardinalite `1 job -> n runs provider`
    - soit restreindre explicitement le flag batch a `Level A` dans la configuration produit et la doc tant que ce contrat n'existe pas
- Risque residuel:
  - Il n'existe pas encore de sweep global des jobs dont `provider_reconcile_due_at <= now`. La reprise durable repose sur la chaine de self-invocation du worker et sur les retriggers ulterieurs.
  - Correction proposee:
    - ajouter un cron/worker de scan qui claim les jobs batch dus et lance `trigger=reconcile`
    - monitorer les jobs `processing + batch` dont `provider_reconcile_due_at` est stale pour detecter les orphelins
- Risque residuel:
  - Les nouveaux statuts operateur ne sont pas encore exposes cote UI/hub metier.
  - Correction proposee:
    - EST-426 doit deriver les etats visibles `submitted_to_provider`, `awaiting_provider_result`, `provider_failed`, `orphan_to_reconcile` depuis les colonnes batch et les outcomes worker
- Risque residuel:
  - Un conflit de merge reste probable sur `processor.ts`, `async-worker.ts` et `types.ts`, qui sont des surfaces partagees entre tickets takeoff.
  - Correction proposee:
    - merger rapidement apres validation
    - privilegier les cherry-picks ou une integration manuelle fichier par fichier sur ces modules
