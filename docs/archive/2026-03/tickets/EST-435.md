## Objectif produit
- Sur une affaire tout juste creee, rendre la premiere action evidente:
  deposer le dossier de consultation pour lancer l'analyse.
- Eviter d'exposer trop tot les surfaces de controle, de validation et de sortie qui ne sont pas encore pertinentes.

## Contexte
- `EST-433` a remplace le panneau pedagogique par un bloc `Prochaine etape`.
- `EST-434` a durci la disclosure progressive et la convergence du flux principal.
- Sur une affaire neuve, le bloc compact actuel reste encore trop abstrait: il ne montre pas assez fortement que le premier geste attendu est le depot des pieces.

## Probleme a resoudre
- l'etat `0 piece` n'est pas assez different des etats plus avances;
- la prochaine action reelle est un depot de dossier, mais l'UI reste polluee par des surfaces aval;
- la carte de depot en tete est aujourd'hui doublee par un second bloc intake visible plus bas;
- le regard de l'utilisateur n'est pas assez guide vers un geste unique a tres faible ambiguite.

## Scope
- Ajouter dans `AffaireFlowHierarchyPanel` un etat dedie `affaire neuve / dossier vide`.
- Dans cet etat, afficher dans `PROCHAINE ETAPE` une grande carte de depot inspiree d'une table de travail.
- Faire de cette carte l'entree dominante du flux:
  - ouverture directe du file picker intake depuis le clic,
  - plus de scroll qui donne l'impression d'une deuxieme action identique.
- Simplifier le hub quand l'affaire est vide:
  - masquer les surfaces aval non pertinentes (`Pilotage`, `Registre`, `Approbation`, `Journal`, timeline detaillee, resume financier),
  - conserver l'intake comme point d'entree technique, mais en mode minimal pour ne pas dupliquer le message d'en tete.
- La carte et cet etat simplifie doivent disparaitre des qu'au moins une piece ou une base de devis existe.
- Une fois au moins une piece deposee, remplacer le bloc compact `Prochaine etape` par une carte de resultat orientee diagnostic metier quand le contexte s'y prete.

## Hors scope
- Suppression ou refonte du banner `AffaireCreatedOnboardingBanner`.
- Refactoring global du cockpit.
- Drag and drop fonctionnel directement dans `AffaireFlowHierarchyPanel`.
- Changement des suggestions cockpit serveur.

## Definition of done
- [ ] Quand `documents.length === 0` et qu'aucune piece n'a encore ete deposee, `PROCHAINE ETAPE` affiche une grande carte de depot
- [ ] Le clic sur la carte ouvre directement le file picker intake sans demander a l'utilisateur de retrouver un second bloc de depot
- [ ] Le hub masque ou compacte les surfaces aval tant que l'affaire est vide
- [ ] L'intake technique reste disponible mais ne duplique plus la promesse de la carte d'entree
- [ ] Des qu'une piece ou une base devis existe, l'etat revient au hub normal
- [ ] Quand l'intake ou le cockpit produisent un diagnostic clair, `Prochaine etape` affiche une carte visuelle `etat result + CTA`
- [ ] Tests unitaires mis a jour
- [ ] Verification locale ciblee executee

## Etat d'implementation au 2026-03-12
- `AffaireFlowHierarchyPanel` est maintenant pilote par un etat hero explicite:
  - `processing`
  - `review`
  - `primary_selection_required`
  - `missing`
  - `brief`
  - `structure`
  - `plans`
  - `ready_to_continue`
- Le tri de priorite applique dans le code suit deja les invariants:
  - `review` domine `missing`
  - `primary_selection_required` domine `missing`
  - un choix `DPGF` ou `CCTP` devient `complementaire` si un principal existe deja
- Le hero compresse les cas charges:
  - `2` valides explicites max
  - `1` review active max
  - `2` missing explicites max
  - puis cartes de resume
- Le panneau bas suit l'etat dominant:
  - `review` => preuve operatoire et autres reviews
  - `primary_selection_required` => arbitrage principal
  - `missing` => pieces deja recues
- Les wording `missing` dans un hero `review` sont degrades en:
  - `NON DETECTE`
  - plutot que `MANQUANT`
  pour eviter un constat trop absolu avant confirmation de la piece active

## Contrat UX
- L'etat `affaire neuve` est un cas special, pas un design permanent.
- Une seule action dominante visible: deposer les pieces.
- Le style illustratif est reserve a `0 piece`.
- Les surfaces de controle n'apparaissent que quand le contexte les rend utiles.
- Le composant doit rester lisible sur desktop et mobile.
- Quand `Prochaine etape` porte deja l'action dominante, les surfaces aval du hub doivent repasser en mode preuve / controle:
  - pas de doublon de CTA dans la command bar,
  - pas de doublon dans le pilotage (`Ajouter des pieces`, `Ouvrir le brief`, `Demarrer l'analyse`) si le hero porte deja cette etape,
  - pas de `Confirmer le brief` redondant dans la carte brief,
  - pas de `Analyser les plans` redondant dans la carte plans,
  - pas de `Ajouter des fichiers` ou `Ajouter les pieces manquantes` repetes si le hero les porte deja.
- Apres upload, la carte doit raconter l'etat du dossier en une lecture:
  - ce qui bloque ou debloque,
  - ce que l'utilisateur doit faire maintenant,
  - pourquoi.

## Règle principale / complémentaire
- Plusieurs documents `DPGF` et `CCTP` sont autorisés dans le dossier.
- Un seul `DPGF principal` et un seul `CCTP principal` sont autorisés au maximum.
- Le hero doit afficher les documents validés, à confirmer et manquants dans la même zone visuelle.
- Si un `DPGF` ou `CCTP` principal existe déjà, une reclassification review vers cette catégorie doit annoncer un classement `complémentaire`, pas un remplacement implicite.
- Si un `CCTP principal` existe déjà, une pièce review peut devenir `CCTP complémentaire` sans friction particulière, mais jamais comme équivalent strict du principal.
- Si plusieurs `DPGF` ou `CCTP` existent sans principal défini, le hero doit afficher une alerte non bloquante:
  - `Aucun DPGF principal`
  - `Aucun CCTP principal`
- Si plusieurs `DPGF` existent sans principal:
  - les automatismes d'analyse / comparaison peuvent continuer,
  - les automatismes engageants doivent rester limités tant que le principal n'est pas choisi.
- Les plans restent multiples sans notion obligatoire de principal global.
- Si plusieurs documents restent à confirmer, le hero ne montre qu'une pièce review active et résume les autres sous la forme:
  - `Autres pieces a confirmer (n)`
- La pièce review active doit être choisie avec cette priorité:
  - elle peut lever un manque critique,
  - puis confiance la plus faible,
  - puis ordre stable.
- Le hero doit expliciter cette priorité via la bulle `Pourquoi ?` avec des indices du type:
  - `Peut lever: DPGF manquant`
  - `Peut lever: Plans manquants`
  - `Peut lever: CCTP manquant`

## State machine formelle — Hero et panneau bas
### Entrees du moteur
- `documents[]`
- `documentsReview[]`
- `documentsValidated[]`
- `documentsValidatedPrimary[]`
- `documentsValidatedSecondary[]`
- `missingPieces[]`
- `missingCritical[]`
- `missingWarning[]`
- `noPrimaryDpgf`
- `noPrimaryCctp`
- `briefStatus`
- `structureStatus`
- `plansStatus`
- `processingStatus`

### Definitions metier
- `document valide`:
  - document classe dans une categorie metier exploitable
- `document review`:
  - document encore `a confirmer` / `a classer`
- `document principal`:
  - `DPGF principal` ou `CCTP principal`
- `document complementaire`:
  - document valide du meme type qu'un principal deja defini
- `piece manquante`:
  - categorie toujours non detectee a ce stade du tri

### Priorite absolue des etats
1. `PROCESSING`
2. `REVIEW`
3. `PRIMARY_SELECTION_REQUIRED`
4. `MISSING`
5. `BRIEF`
6. `STRUCTURE`
7. `PLANS`
8. `READY_TO_CONTINUE`

### Attributs de contexte
- `reviewImpact`:
  - `critical_missing`
  - `standard`
- `missingSeverity`:
  - `critical`
  - `warning`
- `missingDisposition`:
  - `required`
  - `acknowledged`
  - `deferred`
- `readinessLevel`:
  - `not_ready`
  - `ready_with_reservations`
  - `ready`

### Regles de transition
#### `PROCESSING`
- condition:
  - upload ou classification encore en cours
- hero:
  - montrer les pieces recues
  - ne pas afficher de `missing` comme certitude forte
- panneau bas:
  - masquer ou compacter fortement

#### `REVIEW`
- condition:
  - au moins une piece review
  - la piece review active peut avoir:
    - `reviewImpact = critical_missing`
    - ou `reviewImpact = standard`
- hero:
  - action dominante = confirmer la categorie
  - afficher:
    - documents structurants valides
    - 1 piece review active
    - eventuels `missing` comme contexte secondaire uniquement
  - la piece review active est choisie selon:
    - peut lever un manque critique
    - confiance la plus faible
    - ordre stable
  - si `reviewImpact = critical_missing`:
    - le hero doit l'expliciter dans `Pourquoi ?`
    - exemple:
      - `Peut lever: DPGF toujours non detecte`
      - `Peut lever: Plans toujours non detectes`
- panneau bas:
  - preuve operatoire de la piece active
  - autres pieces a confirmer

#### `PRIMARY_SELECTION_REQUIRED`
- condition:
  - plusieurs `DPGF` valides sans `DPGF principal`
  - ou plusieurs `CCTP` valides sans `CCTP principal`
- hero:
  - action dominante = choisir le document principal
  - afficher:
    - `2 DPGF`, `Principal a definir`
    - ou `2 CCTP`, `Principal a definir`
  - ne pas laisser un `missing` ou un warning concurrencer cette action
- panneau bas:
  - arbitrage operatoire uniquement
  - comparaison simple des documents concernes
  - aucune re-explication du hero

#### `MISSING`
- condition:
  - aucune review dominante
  - au moins une piece critique ou d'attention toujours non detectee
- hero:
  - action dominante = ajouter la piece manquante depuis sa carte
  - afficher:
    - ce qui est deja reconnu
    - ce qui manque encore
  - chaque carte manquante porte:
    - son type
    - sa gravite `Critique` ou `Attention`
    - son action `Ajouter`
  - si le manque n'est pas encore ferme metierement:
    - preferer un wording:
      - `Toujours non detecte a ce stade`
      - plutot que `Manquant` trop absolu
  - un manque peut porter un statut:
    - `required`
    - `acknowledged`
    - `deferred`
- panneau bas:
  - uniquement les pieces deja recues
  - jamais la liste des manquants si le hero la porte deja

#### `BRIEF`
- condition:
  - intake exploitable
  - plus de review dominante
  - plus de manque critique bloquant
- hero:
  - action dominante = `Confirmer le brief`
  - afficher les documents structurants reconnus
- panneau bas:
  - contexte de cadrage metier uniquement

#### `STRUCTURE`
- condition:
  - brief confirme
  - structure non generee
- hero:
  - action dominante = `Generer la structure`
- panneau bas:
  - preuves utiles a la generation

#### `PLANS`
- condition:
  - structure prete
  - plans exploitables
- hero:
  - action dominante = `Analyser les plans`
- panneau bas:
  - details de plans ou contexte takeoff, pas d'inventaire intake

#### `READY_TO_CONTINUE`
- condition:
  - aucun etat plus fort ci-dessus
- hero:
  - bloc compact de prochaine etape
- panneau bas:
  - masque ou tres compact

### Reouverture des etats
- La machine doit accepter qu'un dossier se destabilise apres un nouvel upload.
- Exemples de retours arriere legitimement autorises:
  - `BRIEF -> REVIEW`
  - `STRUCTURE -> PRIMARY_SELECTION_REQUIRED`
  - `PLANS -> REVIEW`
  - `READY_TO_CONTINUE -> REVIEW`
  - `READY_TO_CONTINUE -> MISSING`
- Le systeme ne doit jamais supposer qu'un dossier reste stabilise apres ajout d'un:
  - `DPGF revise`
  - `CCTP modificatif`
  - nouveau jeu de plans
  - additif
  - reponse aux questions

### Mode `continuer quand meme`
- Le produit doit permettre, dans certains cas, d'avancer avec reserves.
- Cas typiques:
  - avancer sans `CCTP`
  - avancer sans certains plans
  - continuer avec hypothese ou traitement manuel
- Cette decision doit etre visible dans l'etat via:
  - `missingDisposition = acknowledged` ou `deferred`
- Le hero ne doit pas traiter un manque accepte comme un blocage visuel au meme niveau qu'un manque critique non traite.

### Niveau de readiness
- La machine doit distinguer:
  - `not_ready`
  - `ready_with_reservations`
  - `ready`
- Cette nuance devient importante avant les etapes:
  - validation interne
  - finish line
  - sortie devis

### Contrat d'affichage du hero
#### Ce que le hero doit toujours faire
- montrer ce que TIMAX a compris du dossier
- montrer ce qui bloque maintenant
- montrer une seule action dominante

#### Ce que le hero ne doit jamais faire
- devenir la liste complete des documents
- afficher plusieurs actions primaires
- repeter mot pour mot le panneau bas

#### Cartes visibles dans le hero
- cartes `valides`:
  - priorite a `DPGF principal`
  - priorite a `CCTP principal`
  - puis documents structurants utiles
- carte `review active`:
  - une seule maximum
- cartes `missing`:
  - max `2` visibles
- cartes `resume`:
  - `Autres valides (n)`
  - `Autres pieces a confirmer (n)`
  - `Autres manquants (n)`

### Contrat d'affichage du panneau bas
#### Raison d'etre
- le panneau bas est un panneau de preuve et de controle
- il ne doit pas etre une deuxieme version du hero

#### Regle par etat
- si hero = `REVIEW`
  - panneau bas = detail operatoire de la review + autres reviews
- si hero = `PRIMARY_SELECTION_REQUIRED`
  - panneau bas = choix operatoire du principal
- si hero = `MISSING`
  - panneau bas = pieces deja recues
- si hero = `BRIEF`
  - panneau bas = resume de cadrage
- si hero = `STRUCTURE`
  - panneau bas = contexte utile a la structure
- si hero = `PLANS`
  - panneau bas = contexte plans / metre

#### Regles de non-repetition
- si un `missing` est visible dans le hero, il ne doit pas etre reliste tel quel dans le panneau bas
- si une piece review est active dans le hero, le panneau bas ne doit pas la re-raconter en grand une deuxieme fois
- si le hero resout deja la lecture du dossier, le panneau bas doit se limiter a l'operatoire

### Regles de selection des categories en review
- `Plans`:
  - toujours multi-documents
  - pas de notion de principal global
- `DPGF`:
  - si aucun principal existe:
    - le document devient `DPGF principal`
  - si un principal existe:
    - le document devient `DPGF complementaire`
- `CCTP`:
  - si aucun principal existe:
    - le document devient `CCTP principal`
  - si un principal existe:
    - le document devient `CCTP complementaire`

### Invariants produit
- `REVIEW` domine toujours `MISSING`.
- `PRIMARY_SELECTION_REQUIRED` domine `MISSING`, mais jamais `REVIEW`.
- Un document ambigu ne peut jamais etre utilise implicitement pour satisfaire un manque critique.
- Un document classe en `DPGF` ou `CCTP` alors qu'un principal existe deja devient `complementaire` par defaut, sauf action explicite de remplacement.
- Le hero n'expose que:
  - la decision active
  - 1 a 2 preuves de contexte utiles
  - un resume du reste
- Le panneau bas n'expose que:
  - les elements a arbitrer
  - les controles
  - les consequences metier

### Exemples de rendu cibles
#### Cas `piece inconnue seule`
- hero:
  - 1 piece review active
  - `DPGF`, `Plans`, `CCTP` toujours non detectes a ce stade
  - action dominante = confirmer la categorie
- panneau bas:
  - detail de la piece

#### Cas `DPGF principal + CCTP principal + 1 review + PLAN manquant`
- hero:
  - `DPGF principal`
  - `CCTP principal`
  - `piece inconnue.pdf`
  - `PLAN MANQUANT`
  - action dominante = confirmer la categorie
- panneau bas:
  - autres pieces a confirmer

#### Cas `2 DPGF sans principal`
- hero:
  - `2 DPGF`
  - `Principal a definir`
  - action dominante = choisir le DPGF principal
- panneau bas:
  - comparaison des 2 DPGF
  - documents principaux et alertes `sans principal`
  - piece review active
  - pieces manquantes critiques
  - resumes de surcharge

## Hardening UX recent
- Etat `sans principal`:
  - le hero doit pousser une seule lecture dominante:
    - `Reference principale a definir`
    - carte courte `2 DPGF` / `2 CCTP`
    - sous-texte `Principal a definir`
  - ne pas repeter ensuite la meme phrase dans plusieurs couches du hero et du panneau bas
  - les blocages secondaires comme `Plans manquants` ne doivent pas concurrencer cette decision
  - le panneau bas `Choix principal` ne doit plus re-expliquer le hero: il sert seulement a l'arbitrage operatoire
- Etats `review + missing`:
  - le `missing` reste visible dans le hero, mais avec un poids visuel inferieur a la piece active a confirmer
  - la piece review reste l'action dominante
  - le `missing` ne doit plus etre repete dans `Blocages a traiter` s'il est deja porte par le hero

## Role du panneau bas
- Le panneau bas ne doit pas repeter le hero.
- Il sert a afficher le detail operatoire non visible dans le hero.
- En `review`:
  - si une seule piece est a confirmer et qu'aucun contexte supplementaire n'est masque par le hero, il disparait completement
  - le hero suffit alors a decider sans seconde couche d'information
  - si plusieurs pieces sont a confirmer, le panneau bas montre les autres pieces a confirmer, pas la piece active du hero une deuxieme fois
  - si le hero a resume une partie du contexte valide, le panneau bas montre `Contexte deja classe`
- En `missing`:
  - le panneau bas montre uniquement les pieces deja recues
  - il ne repete jamais les pieces manquantes

## Reduction du pilotage affaire sous le hero
- Le bloc `Pilotage de l'affaire` ne doit plus concurrencer le hero avec une seconde synthese globale.
- Retirer du pilotage:
  - le sous-titre explicatif generique
  - le badge de synthese `x points a traiter`
  - le panneau intermediaire `Sortie aval` / `Pas encore pertinent`
- Le pilotage garde seulement:
  - la finish line quand elle est vraiment revelable
  - la timeline du flux principal
  - les exceptions a traiter
- Objectif UX:
  - le hero porte le diagnostic
  - le pilotage porte la suite structuree et les exceptions
