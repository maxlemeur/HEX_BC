## Contexte
- Le hub affaire affiche aujourd'hui un panneau `Parcours recommande` en trois cartes de poids visuel proche.
- L'exploration produit et la revue UX montrent que ce panneau explique la taxonomie des parcours avant de faire avancer l'utilisateur.
- L'objectif metier cible reste: recevoir les documents le matin, finir le chiffrage et envoyer le devis en fin de journee.

## Probleme a resoudre
- la lecture initiale du cockpit consomme de l'attention sur `principal / adjacent / legacy` alors que les vraies decisions utiles sont plus bas;
- la hierarchie visuelle donne trop de place au `legacy`;
- les aides secondaires restent visibles meme quand elles n'apportent rien a l'instant T;
- la prochaine action recommandee n'est pas mise au premier plan.

## Scope
- Remplacer le panneau `AffaireFlowHierarchyPanel` par un bloc `Prochaine etape`.
- Afficher un statut court, une phrase de contexte et un CTA primaire unique.
- Afficher les blocages seulement quand ils existent.
- Afficher les aides utiles seulement quand elles sont actionnables dans le contexte courant.
- N'afficher la reprise `legacy` que lorsqu'un fallback reel existe sur l'affaire.

## Hors scope
- Refonte des pages `plans`, `legacy estimate-first` ou `review`.
- Recalcul global des suggestions cockpit.
- Changement du contrat des banners de hierarchie dans les surfaces takeoff.

## Definition of done
- [ ] Le cockpit affaire n'affiche plus trois cartes de meme importance pour `principal`, `adjacent`, `legacy`
- [ ] Le panneau affiche une prochaine action unique et contextuelle
- [ ] Les blocages n'apparaissent que s'ils sont reels et actionnables
- [ ] Les aides secondaires sont masquees tant qu'elles ne sont pas pertinentes
- [ ] Le `legacy` n'apparait que comme reprise exceptionnelle quand un contexte existe
- [ ] Tests unitaires mis a jour
- [ ] Tests E2E impactes mis a jour
- [ ] CI locale ciblee validee

## Contrat UX
- Une seule action dominante visible sans scroll ni lecture dense.
- Le panneau doit pouvoir etre lu en moins de 3 secondes.
- Le regard doit aller dans cet ordre:
  1. statut du dossier,
  2. prochaine action,
  3. blocages,
  4. options secondaires,
  5. legacy si et seulement si necessaire.

## Best practices implementation
- Reutiliser les `cockpitSuggestions` existantes comme source de verite pour la prochaine action avant d'introduire une logique parallele.
- Garder la disclosure progressive stricte: pas de section vide, pas de libelle pedagogue sans impact sur la decision immediate.
- Preserver les actions avec confirmation via le meme handler que la command bar pour ne pas perdre le preview et la tracabilite.
- Degrader visuellement le `legacy` en encart tertiaire, jamais en pilier de meme niveau que l'action principale.
