# EST-101 - Benchmark SQL/perf (bulk update + version patch)

## Objectif
Valider les plans et temps d'execution SQL apres extension de la RPC:

`bulk_update_estimate_items(target_version_id, item_updates, version_patch default null)`

Scenarios cibles:
- Fetch tree editeur (`estimate_items` sur version 3000 lignes)
- Bulk update de 100 lignes via RPC
- Reorder des lignes racine

## Script de reference
- `supabase/benchmarks/est_101_explain_3000_rows.sql`

Le script:
- clone une version existante en mode brouillon,
- insere 3000 lignes de benchmark,
- execute 3 `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)`,
- termine par `ROLLBACK` (aucune persistence des donnees benchmark).

## Protocole d'execution
1. Ouvrir Supabase SQL Editor (ou `psql`) sur l'environnement cible.
2. Executer la migration EST-101 avant benchmark.
3. Executer le script `supabase/benchmarks/est_101_explain_3000_rows.sql`.
4. Copier les sorties `EXPLAIN ANALYZE` (les 3 blocs) dans la section "Resultats".
5. Identifier pour chaque scenario:
- noeud dominant (Index Scan / Bitmap Heap Scan / Seq Scan),
- planning time,
- execution time,
- buffers (`shared hit/read`, `temp read/write`).

## Decision index (evidence only)
- Etat: `Aucun index ajoute`
- Regle:
  - Aucun index supplementaire sans preuve `EXPLAIN ANALYZE`.
  - Si `Seq Scan` dominant est observe avec impact materiel, documenter la proposition d'index (colonnes, cardinalite, write cost) et rerun benchmark avant decision.
- Justification:
  - `Fetch tree` et `Bulk update` n'ont pas de `Seq Scan` dominant sur `estimate_items`.
  - Le scenario `Reorder` est principalement limite par le travail d'ecriture de la RPC (mise a jour massive), pas par un manque d'index de lecture.

## Notes
- Cette campagne couvre uniquement la couche SQL/RPC de EST-101.
- Les mesures doivent etre comparees a froid et a chaud si possible (cache).
